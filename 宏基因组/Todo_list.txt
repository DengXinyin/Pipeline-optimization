## 三、工作流总览

每个 task 的优化按以下 5 步进行：

```
Step 1: 运行原代码 → 生成 <序号>_<task>_original_runtime.log
Step 2: 在 Readme_dxy.Qmd 中记录原代码运行时间、数据量、问题
Step 3: 编写优化代码（scripts_dxy/Script/<script>_update.*）
Step 4: 运行优化代码 → 生成 <序号>_<task>_update_runtime.log
Step 5: 在 Readme_dxy.Qmd 中记录优化后运行时间、优化点
Step 6: 通知 Kimi 同步更新 kimi.Qmd 和 xlsx
Step 7: 运行时间复核与改进点归档
  - 单个 task 的原代码和优化版都运行完成后，由 Kimi 读取以下 4 个文件中该 task 的对应章节：
    1. `Metagenomic_pipeline_optimization_kimi.Qmd`（优化结果展示）
    2. `Readme_dxy.Qmd`（用户记录的原始/优化运行时间、问题、优化点）
    3. `Todo_list.txt`（当前 task 状态与数据）
    4. `宏基因组优化效率统计.xlsx`（效率统计表）
  - 核对原代码与优化版 `real` 时间是否一致、提升效率计算是否正确。
  - 将优化代码的核心改进点（并行化、bug 修复、参数化、失败即停等）补充到 `Todo_list.txt` 对应 task 的“主要优化点”中。
  - 该步骤只读取当前 task 对应章节，不应全量读取其他板块，处理应快速完成。
```

## 四、详细步骤说明

### Step 1：运行原代码

1. 找到对应 task 的原始脚本（`scripts/` 目录）。
2. 编写 `sudo docker run` 命令运行原代码。原代码运行依赖两个只读目录：
   - `/home/xydeng/Metagenomics/project/demo/`：测试数据
   - `/home/xydeng/Metagenomics/scripts/`：原始代码
3. 命令末尾使用 `tee` 保存日志到规范路径：

```bash
2>&1 | tee /home/xydeng/Metagenomics/scripts_dxy/logs/00_check_input_no_raw_original_runtime.log
```

4. 确保命令中使用 `time` 包裹实际运行脚本，以便日志中出现 `real / user / sys`。
5. **默认使用 tmux 在后台运行**，防止 SSH 断开导致任务中断；除交互式调试用的小任务（运行时间 < 1 分钟）外，所有 task 都应通过 tmux 启动（详见第十三章 13.7）。

**示例（单脚本）**：

```bash
sudo docker run --network=host --rm -it --cpus=40 --memory="200g" \
    -v /home/xydeng/Metagenomics/project/demo/data:/data \
    -v /home/xydeng/Metagenomics/scripts:/scripts \
    -v /home/xydeng/Metagenomics/scripts_dxy/Output:/output \
    192.168.30.202:23099/metage_megahit/metage:v2.87 \
    bash -c "
        echo '==========================================' && \
        echo '开始时间: ' && date '+%Y-%m-%d %H:%M:%S' && \
        echo '==========================================' && \
        echo '=== 检查输入文件 ===' && \
        ls -la /data/data.xlsx && \
        echo '=== 开始运行 dealdata.py ===' && \
        time python /scripts/dealdata.py -indir /data -outdir /output && \
        echo '==========================================' && \
        echo '结束时间: ' && date '+%Y-%m-%d %H:%M:%S' && \
        echo '=========================================='
    " 2>&1 | tee /home/xydeng/Metagenomics/scripts_dxy/logs/00_check_input_no_raw_original_runtime.log
```

**示例（多脚本组合）**：

```bash
bash -c "
    echo '==========================================' && \
    echo '开始时间: ' && date '+%Y-%m-%d %H:%M:%S' && \
    ...
    echo '=== 开始运行 dealdata.py 和 check_fastq_mapping.py ===' && \
    time (python /scripts/dealdata.py ... && python /scripts/check_fastq_mapping.py ...) && \
    ...
" 2>&1 | tee /home/xydeng/Metagenomics/scripts_dxy/logs/01_<task>_original_runtime.log
```

### Step 2：在 Readme_dxy.Qmd 中记录原代码

在 `Readme_dxy.Qmd` 对应 task 章节中记录：

- 原代码运行命令
- 数据量（样本数、分组、文件格式、数据大小）
- 运行时间（`real` 时间）
- 遇到的问题

### Step 3：编写优化代码

1. 在 `scripts_dxy/Script/` 下创建优化版脚本，文件名加 `_update` 后缀
2. 保留原代码不动
3. 优化方向示例：
   - 并行化（GNU parallel、多线程）
   - 修复 bug（挂载点、分隔符解析等）
   - 参数化（argparse 替代 sys.argv）
   - 兼容性修复（如 R 脚本 `fill = TRUE`）
   - 失败即停（`set -euo pipefail`、`--halt soon,fail=1`）

### Step 4：运行优化代码

与 Step 1 类似，但运行 `scripts_dxy/Script/` 下的优化版脚本，日志保存为：

```bash
2>&1 | tee /home/xydeng/Metagenomics/scripts_dxy/logs/00_check_input_no_raw_update_runtime.log
```

**挂载约定**：
- 原代码目录 `/home/xydeng/Metagenomics/scripts/` 仍按原方式挂载（用于对比或调用未改动的辅助脚本）。
- 优化代码目录 `/home/xydeng/Metagenomics/scripts_dxy/Script/` 必须挂载为容器内的 `/scripts` 或 `/root/microbiome/microbiome/metage_megahit`（根据脚本实际路径选择）。
- 示例：`run_docker_dealdata.sh` 中原代码挂载 `-v /home/xydeng/Metagenomics/scripts:/scripts`，优化代码可改为 `-v /home/xydeng/Metagenomics/scripts_dxy/Script:/scripts`。

**后台运行**：同样默认使用 tmux（第十三章 13.7）。

### Step 5：在 Readme_dxy.Qmd 中记录优化后结果

记录：

- 优化后运行命令
- 优化后运行时间（`real` 时间）
- 优化点总结
- 优化效果（提升百分比）

### Step 6：通知 Kimi 同步

对用户说以下任一语句：

- "Readme_dxy.Qmd 已更新"
- "更新 kimi Qmd"
- "同步优化结果"
- "<task> 跑完了"

Kimi 会自动读取 `Readme_dxy.Qmd`，并同步更新：

- `Metagenomic_pipeline_optimization_kimi.Qmd`
- `宏基因组优化效率统计.xlsx`

## 六、运行时间记录标准

### 6.1 主要参考指标

运行时间以 Linux `time` 命令输出的 **`real` 时间**（wall-clock time）为准。

```text
real    0mX.XXXs
user    0mX.XXXs
sys     0mX.XXXs
```

### 6.2 指标含义

| 指标 | 含义 | 是否主要参考 |
|------|------|-------------|
| `real` | 程序实际经过的墙上时间（含 I/O 等待、调度） | **是** |
| `user` | 用户态 CPU 时间 | 否 |
| `sys` | 内核态 CPU 时间 | 否 |

### 6.3 操作规范

1. 单脚本运行：
   ```bash
   time python /scripts/<script>.py ...
   ```

2. 多脚本组合运行：
   ```bash
   time (python /scripts/<script1>.py ... && python /scripts/<script2>.py ...)
   ```

3. **禁止仅依赖程序自身的中文耗时输出**（如 `✅ 完成！耗时: 1.223秒`、`⏱️ 总耗时: 0.319 秒`），这类输出**仅作辅助参考**。

   > ⚠️ **注意**：程序内部统计的耗时通常只包含 Python/R 脚本逻辑执行时间，不包含以下时间：
   > - Docker 容器启动时间
   > - conda 环境激活时间
   > - 输入数据加载 / I/O 等待时间
   > - 镜像缓存预热、文件系统挂载等外部开销
   > 
   > 因此，脚本内部耗时可能明显小于用户实际等待的时间。**统一以 `time` 命令输出的 `real` 时间为准**。

4. 提取 `real` 时间：
   ```bash
   grep -E "^real" /home/xydeng/Metagenomics/scripts_dxy/logs/01_<task>_original_runtime.log
   grep -E "^real" /home/xydeng/Metagenomics/scripts_dxy/logs/01_<task>_update_runtime.log
   ```

每个 task 按以下顺序组织：

1. 原代码路径及运行方式代码
2. 优化后代码路径及运行方式代码
3. 主要优化点及优化结果（含 8 列表格）

## 十三、参考意见与最佳实践

以下内容来自本项目的实际优化经验，作为后续工作流改进、质量检查和日常操作的参考。其中 13.7~13.8 为 task 单元的具体操作规范与目录约定，新接入项目的人员建议优先阅读。

### 13.1 Task 项目编号规范

1. **严格按 WDL 主流程确定 task 编号**
   - 以 `metage_megahit.wdl` 中 `isbwa == "yes"` 主流程的 `call` 调用顺序为准。
   - 例如：`check_input_with_raw` → `kneaddata_no` → `megahit_no` → `bins` → ... → `resFile` 依次编号为 01~21。

2. **非 WDL task 不占用 WDL task 编号**
   - `R 脚本修改（sample-metadata.tsv）` 是兼容性修改，不是 WDL task，不分配序号。
   - `check_input_no_raw` 仅出现在 `isbwa == "no"` 分支，不属于 WDL 主流程 task，建议作为前置/附录处理。
   - 如果需要排序，可自定义前缀（如 `00_`），但必须在文档中明确说明其非 WDL task 属性。

3. **避免历史编号与新编号冲突**
   - 一旦确定编号体系，后续优化应尽量保持一致。
   - 如需整体重排编号，必须同步重命名所有 log 文件，并更新所有 QMD、Excel、Todo_list 中的引用。

### 13.2 Log 文件编号与 Task 编号同步

1. **Log 文件名格式**

   ```text
   <序号>_<task_name>_<original|update>_runtime.log
   ```

2. **序号必须与 task 编号一致**
   - `Task 1: check_input_with_raw` 对应 `01_check_input_with_raw_*.log`。
   - `Task 3: megahit_no` 对应 `03_megahit_no_*.log`。
   - 非 WDL task 如使用自定义序号（如 `00_check_input_no_raw_*.log`），需在 Todo_list 中单独说明。

3. **重排编号时必须同步更新**
   - 重命名 `scripts_dxy/logs/` 下的所有 log 文件。
   - 全文搜索并替换 `Metagenomic_pipeline_optimization_kimi.Qmd`、`Readme_dxy.Qmd`、`Todo_list.txt` 中的旧路径。
   - 同步更新 `宏基因组优化效率统计.xlsx` 中的顺序和路径。

### 13.3 QMD 文档标题一致性检查

1. **二级标题 `## N.M` 必须与 Task 编号一致**
   - 例如 `Task 3: megahit_no` 下应为 `## 3.1`、`## 3.2`、...、`## 3.7`。
   - 非 task 章节（如 R 脚本修改）可使用 `## R.1`、`## R.2` 或纯文字标题。

2. **三级标题 `### N.M.K` 必须与其父级二级标题一致**
   - 例如 `## 3.6 原代码内容` 下应为 `### 3.6.1`、`### 3.6.2`。
   - 避免出现 `## 3.7 优化代码内容` 下面是 `### 4.7.1` 的错位。

3. **重排/重组 Task 后必须执行标题检查**

   可用以下命令快速检查所有 `### ` 子标题的父级编号是否一致：

   ```bash
   cd /home/xydeng/Metagenomics/scripts_dxy
   grep -n "^### " Metagenomic_pipeline_optimization_kimi.Qmd
   grep -n "^## [0-9RP]\." Metagenomic_pipeline_optimization_kimi.Qmd
   ```

   也可以编写脚本自动检查：对每个 `### N.M.K`，确保其前面最近的 `## N.M` 中的 `N` 相同。

### 13.4 多文件同步检查清单

修改 task 编号、log 路径或章节结构后，必须检查以下文件是否同步：

| 文件 | 需要同步的内容 |
|------|---------------|
| `Metagenomic_pipeline_optimization_kimi.Qmd` | Task 编号、章节标题、log 路径、顶部汇总表、Task 汇总表 |
| `Readme_dxy.Qmd` | log 路径引用 |
| `Todo_list.txt` | 编号顺序表、示例日志名、工作流说明 |
| `宏基因组优化效率统计.xlsx` | task 顺序、代码位置、时间数据 |
| `scripts_dxy/logs/` | log 文件名 |

### 13.5 未优化 Task 占位章节规范

1. **优先写入占位框架**
   - 即使尚未运行和优化，也应先把未优化 task 的代码路径、WDL 调用方式、输入输出说明写入 `kimi.Qmd`。
   - 这样能保持文档完整性，也方便后续直接填充优化结果。

2. **占位章节应包含**
   - 原代码路径
   - 优化后代码路径（标记“待创建”）
   - WDL 调用方式
   - 本地 Docker 测试命令占位
   - 优化结果表格占位
   - 输入/输出数据说明
   - 原代码内容（可选，待补充）

3. **避免占位章节标题错位**
   - 使用脚本生成占位章节时，应确保生成的 `## N.M` 和 `### N.M.K` 与 task 编号匹配。

### 13.6 建议的自动化检查脚本

可在 `scripts_dxy/` 下维护一个简单检查脚本，例如 `check_qmd_headers.py`，在每次重排 task 后运行：

```python
#!/usr/bin/env python3
"""检查 kimi.Qmd 中 Task 章节标题是否一致。"""
import re
from pathlib import Path

p = Path('Metagenomic_pipeline_optimization_kimi.Qmd')
text = p.read_text(encoding='utf-8')
lines = text.splitlines()

current_task = None
errors = []
in_code = False

for i, line in enumerate(lines, 1):
    if line.strip().startswith('```'):
        in_code = not in_code
        continue
    if in_code:
        continue

    if line.startswith('# '):
        if line.startswith('# Task '):
            current_task = re.match(r'^# Task (\d+):', line).group(1)
        elif 'R 脚本修改' in line:
            current_task = 'R'
        elif 'check_input_no_raw' in line:
            current_task = 'P'
        else:
            current_task = None

    if current_task and line.startswith('## '):
        m = re.match(r'^## (\d+|R|P)\.(\d+) ', line)
        if m and m.group(1) != current_task:
            errors.append((i, line, current_task))

    if current_task and line.startswith('### '):
        m = re.match(r'^### (\d+|R|P)\.(\d+(\.\d+)?) ', line)
        if m and m.group(1) != current_task:
            errors.append((i, line, current_task))

if errors:
    for ln, line, task in errors:
        print(f'第 {ln} 行标题不一致: {line.strip()} (当前章节 Task {task})')
else:
    print('所有 Task 章节标题一致。')
```

在每次大规模调整文档结构后运行该脚本，可以避免标题错位问题。

### 13.7 Task 单元运行操作规范

#### 13.7.1 基本运行模板

每个 task 的运行命令应遵循以下结构：

```bash
cd /home/xydeng/Metagenomics

sudo docker run --network=host --rm -it \
    --cpus=<CPU数> --memory="<内存大小>" \
    -v /home/xydeng/Metagenomics/project/demo/data:/data \
    -v /home/xydeng/Metagenomics/project/demo/rawdata:/rawdata \
    -v /home/xydeng/Metagenomics/project/demo/metadatadir:/metadatadir \
    -v /home/xydeng/Metagenomics/scripts:/scripts \
    -v /home/xydeng/Metagenomics/scripts_dxy/Output:/output \
    192.168.30.202:23099/metage_megahit/metage:v2.87 \
    bash -c "
        echo '==========================================' && \
        echo '开始时间: ' && date '+%Y-%m-%d %H:%M:%S' && \
        echo '==========================================' && \
        echo '=== 检查输入文件 ===' && \
        ls -la /data /rawdata /metadatadir && \
        echo '=== 开始运行 <脚本> ===' && \
        time python /scripts/<script>.py ... && \
        echo '==========================================' && \
        echo '结束时间: ' && date '+%Y-%m-%d %H:%M:%S' && \
        echo '=========================================='
    " 2>&1 | tee /home/xydeng/Metagenomics/scripts_dxy/logs/<序号>_<task>_original_runtime.log
```

**要点**：
- `--network=host`：容器使用宿主机网络，便于访问内网资源。
- `--rm`：运行结束后自动删除容器，避免残留。
- `-it`：交互式终端，便于在 tmux 中查看输出；如通过脚本后台运行且无 tty，可去掉 `-t`。
- `time`：必须用 `time` 包裹实际运行命令，确保日志中出现 `real / user / sys`。
- `tee`：在**宿主机**端执行，同时输出到屏幕和日志文件，因此无需把 `logs/` 挂载进容器。

#### 13.7.2 使用 tmux 后台运行

单个 task 可能运行数分钟到数小时，**默认使用 `tmux` 在后台运行**，避免 SSH 断线导致任务中断或日志丢失。

**命名规范**：建议会话名与 task 对应，例如 `megahit_original`、`megahit_update`、`prodig_original`、`prodig_update` 等，便于识别和管理。

**常用命令速查**：

| 操作 | 命令 | 说明 |
|------|------|------|
| 新建会话并进入 | `tmux new -s <task_name>` | 创建后立即进入该会话 |
| 新建会话但不进入（后台创建） | `tmux new -s <task_name> -d` | 适合脚本中预创建会话 |
| 在会话中运行命令后 detach | `tmux new -s <task_name> "./run.sh"` | 命令结束后会话仍保留，可 attach 查看 |
| 退出当前会话（后台运行） | `Ctrl+B`，再按 `D` | 会话继续运行，可稍后重新接入 |
| 查看所有会话 | `tmux ls` | 列出会话名、窗口数、创建时间、当前状态 |
| 重新接入会话 | `tmux attach -t <task_name>` | 缩写：`tmux a -t <task_name>` |
| 从其他会话切换 | `tmux switch -t <task_name>` | 已 attach 某个会话时使用 |
| 重命名会话 | `tmux rename-session -t <old_name> <new_name>` | 便于规范化管理 |
| 结束指定会话 | `tmux kill-session -t <task_name>` | 强制关闭该会话及其所有进程 |
| 结束所有 tmux 会话 | `tmux kill-server` | 谨慎使用，会关闭全部会话 |
| 在会话内温和停止任务 | 按 `Ctrl+C` | 仅停止当前前台命令，会话保留 |

**标准操作流程示例**：

```bash
# 1. 进入工作目录
cd /home/xydeng/Metagenomics/scripts_dxy

# 2. 新建 tmux 会话（例如运行 megahit 原代码）
tmux new -s megahit_original

# 3. 在 tmux 会话内执行运行命令
./run_03_megahit_no_original.sh 2>&1 | tee logs/03_megahit_no_original_runtime.log

# 4. detach 到后台：按 Ctrl+B，再按 D

# 5. 之后可随时查看进度
tmux ls
tmux attach -t megahit_original

# 6. 任务跑完或需要强制结束时
tmux kill-session -t megahit_original
```

**注意事项**：
- 使用 `sudo docker run` 时，推荐在 tmux 会话内执行，这样即使终端断开，docker 容器也会继续运行。
- 若通过脚本批量启动多个 task，建议为每个 task 单独创建 tmux 会话，避免一个会话失败影响其他任务。
- 长时间运行的任务（如 `megahit_no`、`prodig_no`）强烈建议配合 `tee` 保存日志，便于 detach 后通过日志文件查看进度。

#### 13.7.3 中止程序运行

| 场景 | 操作 |
|------|------|
| 在 tmux 内温和停止 | 按 `Ctrl+C` 一次，脚本会停止当前命令并退出 |
| 强制结束整个 tmux 会话 | `tmux kill-session -t <task_name>` |
| 只停止当前 docker 容器，保留 tmux 会话 | `sudo docker ps` 找到容器 ID，然后 `sudo docker stop <容器ID>` |
| 批量顺序运行脚本中途停止 | 按 `Ctrl+C` 一次，脚本因 `set -e` 退出，后续 task 不再执行 |

## 十四、样本核对与全阶段指纹管理（sample_double_check）

### 14.1 设计目标

在宏基因组流程的任意阶段，客户都可能对样本进行**增加、删减或重命名**。为避免直接覆盖已有结果、遗漏样本或无法追溯中间文件来源，引入 `sample_double_check.py` / `sample_double_check.sh`：

- **前置核对**：在流程最开始比较当前 `sample.txt` 与上次 manifest，识别新增/删除/重命名/内容变更样本。
- **全阶段指纹记录**：不仅记录原始 FASTQ，还可被每个 task 调用，记录该阶段输入/输出文件指纹（大小、修改时间、MD5）。
- **合并文件支持**：支持记录由多个样本合并产生的中间文件（如 `all.fa`、`unique_gene.fasta`），并记录其来源样本。
- **结果目录同步**：对删除/重命名/内容变更样本，自动清理或重命名下游结果文件。

### 14.2 脚本位置

| 脚本 | 路径 | 说明 |

| Docker 运行脚本 | `/home/xydeng/Metagenomics/scripts_dxy/Script/sample_double_check.sh` | 在 tmux 会话中调用 Docker 运行 `check-raw` 子命令 |

### 14.7 注意事项

1. **默认 dry-run**：`check-raw` 不加 `--apply` 不会修改任何文件，适合先核对。
2. **结果目录同步**：通过 `--output-dirs` 指定需要同步的目录，默认支持 `cleandata`、`de_host`、`megahit_update`、`prodigal_original`、`bowtie` 等。复杂目录（如 `Result` 中的 group-level Excel）可能需要额外配置或手动处理。
3. **重命名匹配**：基于文件 MD5（或大小+修改时间）进行匹配。若两个不同样本的 FASTQ 文件内容完全相同，可能会被误判为重命名。
4. **合并文件**：`record-stage` 的 `--merged` 参数用于标记由多个样本合并产生的文件（如 `all.fa`、`unique_gene.fasta`），`input_samples` 记录其来源。
5. **跳过不存在文件**：`record-stage` 支持 `--skip-missing`，在 WDL 中某些文件可能因参数不同而不生成时使用（如 `host=none` 时无 host 文件）。
6. **目录输出**：`record-stage` 默认无法计算目录 MD5。对目录输出可加上 `--no-md5`，仅记录目录大小和修改时间；或改为记录目录内具体文件。
7. **并发写入安全**：`ManifestManager.save()` 使用文件锁（`fcntl`）+ 临时文件原子重命名，WDL 多个 task 同时写入 `<metadatadir>/.sample_manifest.json` 不会互相覆盖或读取到半写入文件。
8. **该脚本不直接运行下游分析**：它只负责样本核对和结果目录同步。新增/内容变更样本需由 `Kneaddata_update.py`、`megahit_update.py` 等下游脚本读取 `samples_to_process.txt` 后处理。
9. **扩展到每个 stage 的可行性**：技术上容易实现。推荐两种方式：
   - **Python task 脚本**：直接 `from sample_double_check import ManifestManager` 调用 `record_stage()`。
   - **WDL 工作流**：在每个 task 的 `command` 块末尾追加 `python sample_double_check.py record-stage ...` 调用（详见 14.8）。
   建议逐步接入：先在 `megahit_update.py`、`prodigal.py`、`bwa.py` 等核心脚本中增加记录调用。

### 14.8 WDL 工作流集成方式

可以在现有 WDL 工作流基础上直接追加 `record_stage()` 调用，无需重构原有逻辑。

#### record_stage() 在 WDL 中的行为

- **只读取文件**：计算 `size`、`mtime`、`md5`，不会修改、移动或删除被记录的文件。
- **只写入 manifest**：更新 `<metadatadir>/.sample_manifest.json`。
- **失败安全**：如果 task 主命令失败，`record_stage()` 不会执行，manifest 保持原状。

#### 前置条件

1. Docker 镜像中可用 Python 3（脚本仅依赖标准库）。
2. `scripts_dxy/Script/` 挂载到容器内 `/root/microbiome/microbiome/metage_megahit/` 或 `/scripts/`。
3. `metadatadir` 必须挂载为容器内**可写**路径。

#### WDL 集成基本原则

若后续决定接入 WDL，按以下原则在每个 task 的 `command` 块末尾追加 `record-stage`：

- 单样本 task 循环记录（rawdata、cleandata、megahit、bwa）。
- 合并输出 task 记录（prodigal、annotation、统计、汇总等）。
- 为没有 `datapath` 输入的 task（`tax_anno`、`func_anno`、`anno`、`VCA_anno`、`MBQ_anno`、`bins_stats`）需要手动添加输入并更新 workflow 调用。
- 目录输出使用 `--no-md5` 避免 `IsADirectoryError`。
- 可能不存在的文件（如 `bwa` 索引、host 相关文件）使用 `--skip-missing`。
- 并发安全：`sample_double_check.py` 的 `save()` 已使用文件锁 + 原子写入，WDL 多 task 同时写入 manifest 不会互相覆盖。

#### 单样本输出 task 示例（megahit_no）

```wdl
task megahit_no {
    String metadatadir
    String cleandatadir
    String megahit_dir
    String host

    command {
        source /root/anaconda3/etc/profile.d/conda.sh
        conda activate megahit
        python /root/microbiome/microbiome/metage_megahit/megahit.py \
            -I ${metadatadir} --cleandir ${cleandatadir} --host ${host} \
            --host_dir /de_host --megahit ${megahit_dir}

        # 记录每个样本的组装结果指纹
        for sample in $(awk 'NR>1 {print $2}' ${metadatadir}/sample.txt); do
            if [ -d "${megahit_dir}/${sample}" ]; then
                python /root/microbiome/microbiome/metage_megahit/sample_double_check.py record-stage \
                    -I ${metadatadir} \
                    --stage megahit \
                    --key ${sample} \
                    --files ${megahit_dir}/${sample}/final.contigs.fa ${megahit_dir}/${sample}/log \
                    --input-samples ${sample}
            fi
        done
    }
    runtime { ... }
}
```

#### 合并输出 task 示例（prodig_no）

```wdl
task prodig_no {
    String metadatadir
    File megahit
    String prodigal_dir

    command {
        source /root/anaconda3/etc/profile.d/conda.sh
        conda activate megahit
        python /root/microbiome/microbiome/metage_megahit/prodigal.py \
            --megahit ${megahit} --cdhitdir /app/cd-hit-v4.8.1-2019-0228

        # 记录合并产生的非冗余基因集指纹
        all_samples=$(awk 'NR>1 {print $2}' ${metadatadir}/sample.txt | tr '\n' ' ')
        python /root/microbiome/microbiome/metage_megahit/sample_double_check.py record-stage \
            -I ${metadatadir} \
            --stage prodigal \
            --key all \
            --files ${prodigal_dir}/all.fa ${prodigal_dir}/unique_gene.fasta \
            --input-samples ${all_samples} \
            --merged
    }
    runtime { ... }
}
```

#### 推荐接入顺序

按流程顺序逐步在每个 task 末尾加入 `record-stage`：

```
check_input_with_raw → kneaddata_no → megahit_no → [bins → bins_drep → quant_classify → bins_stats]
                         ↓               ↓
                    record_stage  record_stage
                         ↓               ↓
                    cleandata     megahit
                         ↓               ↓
                              prodig_no → bwa_no → tax_anno / func_anno → anno
                                ↓         ↓          ↓            ↓
                           record_stage record_stage record_stage record_stage
                                ↓         ↓          ↓            ↓
                           prodigal    bowtie     tax_anno    func_anno
```

这样每次 WDL 运行都会自动更新 manifest，后续 `sample_double_check.py check-raw` 可以与 manifest 对比，实现全链路增量核对。
